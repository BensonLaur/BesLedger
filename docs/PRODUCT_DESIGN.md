更新日期：2026-10-23。已按确认的页面和预算基线实现正式应用，本轮同步改进原型与 0.1.3 界面。先满足作者自己的补账、账户和报表需求，再根据实际使用反馈扩展。

本文汇总已经确认的方向和仍需讨论的细节；标为“建议”的部分不等于用户已经接受。专题规则分别见 [短信录入](SMS_WORKFLOW.md)、[短信访问边界](SMS_ACCESS.md)、[退款与周期账](REFUNDS_AND_RECURRING.md) 和 [同步模型](SYNC_MODEL.md)。

### 我的、登录与同步（2026-10-23 更新）

延续原型的分组列表、图标、留白和点击反馈，行为以 [我的与同步设计](MY_PAGE_DESIGN.md) 为准。原型的固定“已连接 · 示例连接”和演示同步弹窗不能直接还原到正式应用。

已实现的 GitHub App 登录保持、自动准备私有存储及设备同步密钥保存必须在改版中保留。将“GitHub 已登录”“本地账本已解锁”“某本账最近已同步”分别展示；登录不上传账本，锁定不退出 GitHub，解锁后自动取用已保存密钥，账目修改后仍需主动同步。账户与账本原有身份不因登录而重建，同名账本不自动合并。

普通用户只需在 GitHub 安装并授权应用，无需自己注册 App、部署登录服务或填写仓库名称。首次授权前用简短文字说明 All repositories 对其他仓库内容的读写能力，详细权限放到可展开说明；不能因界面简化而隐藏实际范围。

### 首页快捷入口与功能扩展

关于月度图形、可选月预算、按时间范围联动的明细与统计下钻的整体关系，见 [首页设计提案](HOME_DESIGN.md)。用户已确定轻立体日历及日常刻度超出折断，接受 P90、历史补样本与稳定更新作为初始规则。完整主预览已整合日历选日、查看整月、返回本月与全部时间，并保留移动端底部“＋ 记一笔”和桌面右上角入口。保存的新记录在当前预览中联动首页与统计；可选预算已纳入第一版，默认关闭。

预算已确认使用概览卡右上角开关，启用后以净支出金额行的圆角淡色背景表示已用比例；保留预算总额和剩余／超额文字。首次启用需设置金额，关闭保留该月设定。各账本、月份独立，全时间汇总不显示单月预算，详见首页专题文档。

用户指出快捷行不应打断“点击日期 → 查看下方明细”的联系。本轮改为首页顶栏“快捷”按钮按需展开浮层：包含短信记账、借贷、周期账、更多功能；手机从底部展开，iPad／电脑在右上方展开。日历和明细直接相接，底部“＋ 记一笔”仍一键进入录入页。账本仍从顶部名称打开，更多功能进入完整功能列表。该布局作为初版基线，后续在真实使用中微调。

快捷入口是导航，采用固定顺序，不套用记账分类的自动频率排序。后续可在全部功能页提供编辑入口，由用户选择、隐藏和手动排序快捷面板项目；建议最多两行，更多功能始终放最后。新功能先进入完整列表，用户有需要再固定到快捷面板。当前只演示固定快捷面板与全部功能页，尚未实现用户定制、拖动排序或跨设备保存偏好。

### 事件页定位

事件表示有日期的财务事项，关联原有资金账户、借贷记录或周期规则，不新增一套独立的金额与余额体系。花呗、借呗只是用户可自建的负债账户示例；当前预览未连接这些服务，也不自动获取应还额。

默认按日期分为“已过期 · 待核对”“今天”“即将到来”。日期已过不代表实际逾期未还，尚未核对时保留待核对语义；未来金额标为本期应还、预计本金、预计收入或预计支出，不能拿账户总欠款替代本期应还额。

周期规则另设管理视图，可查看、暂停、修改规则与历史生成记录。规则对应多个期次事件，修改规则影响后续期次，已生成账单仍可单独修改。暂停规则后不继续显示其未来待生成期次，历史账目保留。

点击还款／收回事项可进入对应转账或借贷记账，预填相关账户与预计金额，由用户核对实际金额、利息及发生时间；事件日期不能直接当作实际交易日期。周期事项打开来源规则。当前预览只演示入口和预填，未实现支付、银行连接、后台通知、已处理状态或自动核销。

正式实现需用来源 ID 与期次 ID 保持关联，避免周期重试产生重复事件。到期本身不影响余额或实际统计；只有已保存的有效账单参与统计。部分还款不能自动视为全部处理，已记账后也需依据关联关系更新事件状态。提醒数据和系统通知分开，PWA 关闭后的准时后台通知仍不作默认承诺。

## 记账页

新建草稿按 [首页默认时间规则](HOME_DESIGN.md#从首页新建账单的默认时间) 初始化，不能始终使用演示日期。

手机端从上到下：账本选择；收入／支出／转账／借贷标签；分类与大字号金额；常用类别；备注；日期时间和账户等字段；数字键盘与“再记”“保存”。转账及借贷按各自语义展示两端账户，不强行套用消费分类。

备注既能输入普通说明，也能粘贴银行短信。建议只在粘贴或主动重新识别时运行解析，避免每改一个字就覆盖用户手动修正的字段。解析成功后四项信息在原位置更新，推断和缺失处提供简短标记；已有手动值与新结果冲突时给出替换选择。具体撤销与替换交互待原型验证。

建议“保存”为保存后返回来源页面，“再记”为保存后继续新草稿。新草稿清空金额、短信和本笔推断结果；保留当前账本与明确的补账上下文。账户、分类是否记住上次选择仍待确认，不能让上笔短信尾号或时间误用于下一笔。

保存成功后才清空草稿；保存失败保留原文和修正值。返回时有未保存内容需明确处理。金额、账户、日期错误在对应字段附近说明；重复短信提示已有记录，允许核对后保留真实重复交易。

成员、商家、标签、附件在参考界面可见，但不是四项识别的必填字段。它们的首期展示和管理范围待讨论，不能仅因截图里存在就纳入完整实现。

### 四种记账入口的统一样式

用户希望收入、支出、转账、借贷的选择区采用一致的圆形设计。金额行下方统一使用“圆形图标＋下方文字”：图标尺寸、文字层级、网格间距和选中样式共用，选中圆面填充产品主色。保留借贷中已经改进的资金图标，不再单独使用整块方形按钮。分类或行为的选择顺序、金额、备注、键盘位置保持一致。

### 转账行为分类

用户提供的挖财截图显示转账、投资、赎回、存钱、取钱五项，用于区分资金转移的行为。BesLedger 预览补上同名五项：点击后更新金额行的名称、图标与选中状态；转出／转入账户仍由用户选择，中间按钮交换两端。切换行为分类不会擅自替换账户，示例账户包含现金与投资账户以便演示。

| 行为 | 常见用途示例 |
| --- | --- |
| 转账 | 银行卡与网络钱包之间划转 |
| 投资 | 银行卡向投资账户划款 |
| 赎回 | 投资账户的资金转回银行卡 |
| 存钱 | 现金存入银行卡 |
| 取钱 | 从银行卡取出现金 |

这些名称属于转账行为属性，与收入／支出分类分开保存，可用于后续查询和行为统计。两端金额相同的内部转移不计普通收入或支出；实际投资收益、亏损、手续费需独立表达，不能将整笔赎回额直接作为收入。加入“投资／赎回”入口不代表首期自动支持行情估值、交易佣金或完整投资管理。

当前预览可保存所选行为及账户方向到本次会话内的示例记录，拒绝同一账户向自己转账；尚无真实持久化或统计计算。示例短信解析仅覆盖普通收支，在转账备注粘贴时保留原文，不把转账自动改成消费。正式转账短信识别、分类管理及是否按行为建议账户方向后续另行确定。

## 分类选择

采用常用类别图标区与完整类别选择面板。完整面板支持大类展开小类，保留搜索、添加与管理入口；用户熟悉的名字优先于重新发明分类体系。

用户已提供各大类和收入的完整截图，现已整理通用内置选项，保留九个支出大类和一级收入分类。个性化细分项由用户自建；退款、贷款本金与投资划款保持专门业务语义，避免误放普通收支。清单与取舍见 [内置分类与排序](CATEGORIES.md) 和 [数据清单](examples/builtin-categories.json)。

用户提出成功使用后自动加入常用候选、按周／月／年频率加权排序，并明确末项固定为“···／全部”。当前建议支出显示 11 个类别加全部，收入显示 7 个类别加全部；按当前账本分别统计最近 7／30／365 天的使用占比，权重 60／30／10，加入冷启动平滑和稳定换位阈值，当前草稿内不重排。具体参数待真实使用验证。挖财官方两级支出／一级收入结构继续作为参考。

建议分类使用稳定 ID，改名不丢失历史关联；停用分类仍可在历史记录与报表中辨认。分类是否跨账本共用、调整父子关系是否改变历史分组，尚待决定。

## 共用账户与余额

账本用于组织记录，资金账户表示实际资产或欠款。同一张银行卡在多个账本使用时引用同一账户身份，不因创建新账本复制一份余额。

### 首次启用与旧账衔接

用户已确认先从启用日的账户状态开始记新账。每个账户记录期初余额或欠款及其对应的起算时点，再累加之后的有效资金变动。期初状态不作为当日收入或支出；共用账户只建立一份期初状态，不随新增账本重复入账。

期初金额已经包含的历史交易不能再次累加。补录早于起算时点的交易时需提示核对期初边界，具体补录与调整交互另行设计。首次录入期初状态和以后对账时校正余额是两种操作。

用户已提供邮件压缩包内的 XLSX 导出文件，完成只读结构检查，结果见 [挖财导出结构与迁移边界](WACAI_EXPORT.md)。第一版继续按期初状态加新账的方式推进，本应用自身的数据导出与恢复仍需早期提供。

本次检查确认：日期文本保留到秒；完整转账将两端放在同一单元格；已验证的还款本金与利息分别导出，主界面的含息总额不直接对应导出本金行。退款带负金额与退款属性。部分旧记录缺少转账一端或往来方，需要待映射处理。

导出列只是交换格式，不能据此推断挖财内部数据库结构。本文件未提供专门的稳定账单 ID、退款原单 ID、周期规则定义与来源字段，也没有完整账户设置和期初状态。BesLedger 保持自己的业务模型，导入适配负责映射和明确缺失项；不承诺仅凭这个导出完整还原挖财。完整私人备份不进入项目仓库。

### 账户类型与余额展示

建议初始账户覆盖现金、储蓄卡、网络钱包、信用卡、应收应付、自定义资产与自定义负债；账户名称可按个人习惯命名。应收应付表示用户自己的债权／债务，不是对方真实银行账户。期初金额和日期需要显式记录；直接校正余额与补记收支的含义不同，调整流程待确认。

用户的账户列表还展示投资账户、储值卡、虚拟账户。先保留为账户分类参考；这些类型是否首期都需要，以及是否包含收益估值等专门能力，不能仅凭存在分组就确定。

### 添加账户的交互草案

用户反馈首版账户类型下拉框不如挖财直观。截图可见选项空间窄、没有图标与用途示例，深色外观下系统菜单还出现浅色文字配白底的问题。账户类型是后续字段的前置选择，建议改为“账户页的＋ → 选择账户类型 → 填写账户信息”。

- 类型页用整行可点的图标列表，直接展示现金、信用卡、储蓄卡／借记卡、网络账户、投资账户、应收／应付、储值卡，并以“其他账户”承接其他资金或欠款；图标旁用短例子解释用途。
- 表单顶部显示已选类型，可返回更换；当前预览按类型保留草稿，避免把储蓄余额自动解释为信用卡欠款。
- 资产用“账户里有多少钱”，信用卡用“还有钱没还／卡里有多存的钱”，应收应付明确“别人欠我／我欠别人”。期初日期单独填写，银行卡尾号可选，用于后续短信匹配。
- 当前只是交互提案。预览中出现投资账户或储值卡，不代表收益估值、自动行情等业务能力已纳入第一版；账户类型的完整范围仍待确认。保存仅演示表单检查，不创建真实账户。

负债账户列表用带符号的余额参与净资产汇总，详情用正数显示“欠款”。信用账户出现正余额时应显示溢缴款／结余，不能对所有金额取绝对值后都叫欠款。信用卡总欠款、已出账应还额和可用额度也不能混为同一数值。

以下均为虚构例子，表达预期计算行为：

| 操作 | 账户变化 | 普通收支统计 |
| --- | --- | --- |
| 信用卡消费 100 元 | 信用卡欠款增加 100 元 | 支出 100 元 |
| 储蓄卡还信用卡本金 100 元 | 储蓄卡余额减少，信用卡欠款减少 | 转账，不重复算消费 |
| 消费退款退回信用卡 30 元 | 信用卡欠款减少 30 元 | 冲减对应支出 |
| 同一消费退款退到钱包 30 元 | 钱包余额增加，信用卡欠款不变 | 冲减对应支出 |
| 从自定义负债账户转入储蓄卡 1,000 元 | 欠款和银行卡余额同时增加 | 本金往来，不是收入 |
| 从储蓄卡转回负债账户 400 元 | 银行卡余额和欠款同时减少 | 本金往来，不是支出 |

当前设备缺少其他账本流水时，不能把局部计算结果称为完整账户余额。页面应标明余额的数据范围、同步时间与完整性。仅云端账本不能按零处理；也不能为了算余额而自动上传原本仅本地的账单。账户级余额投影及同步范围需在实现前定型，见 [同步模型](SYNC_MODEL.md)。

## 基础借贷记账

用户长期用自定义负债账户加转账记录向他人借钱和还钱，这个方式继续有效。基础借贷页是带业务含义的便捷入口，复用账户与资金变动模型，避免再建一套重复余额。

截图确认了借入、借出、还款、收款四项，以及还款日和利息入口。用户实机进一步确认，往来方选择限定为“应收应付”账户，截图的还款与收款选择页支持这一观察；信用卡是独立账户分类。官方计划说明确认有借贷应收应付提醒。截图不能证明挖财是否逐笔匹配借款、如何自动计息，BesLedger 不把这些推断作为已确认需求。

建议借贷页的往来方限定为应收应付账户，普通转账继续允许用户用信用卡或自定义负债账户管理往来。账户类型决定选择范围和附加字段，资金计算共用基础模型；不强制把已有账户重新建账或迁移历史交易。账户类型转换的迁移规则以后另行设计。

### 与转账共用的记账布局

用户明确要求降低借贷页的学习成本，参考挖财熟悉的操作顺序。金额行、账户选择、备注、日期／标签和数字键盘复用普通记账与转账的样式；借入、借出、还款、收款用金额行下方的四个入口切换。根据最新反馈，资金图标采用与收入、支出和转账一致的圆形底，选中圆面填充产品主色，图标下方保留文字。保存与再记始终在同一数字键盘位置。

转账中间按钮可交换两端；借贷中间为不可点击的固定右箭头，始终表达资金从左向右流动。用户已明确往来方初始留空，等待选择应收应付账户，不能预选示例联系人。

| 操作 | 左侧 | 右侧 |
| --- | --- | --- |
| 借入 | 出借方，待选应收应付账户 | 收款资金账户 |
| 借出 | 付款资金账户 | 借款方，待选应收应付账户 |
| 还款 | 付款资金账户 | 出借方，待选应收应付账户 |
| 收款 | 借款方，待选应收应付账户 | 收款资金账户 |

借出右侧采用“借款方”称呼收钱并向用户借钱的人，避免将其与出借资金的用户混淆。借入／借出的到期日、还款／收款的“包含利息”作为可选入口，按需展开；不常驻大块说明和计算面板。有利息时显示简短的本金／利息摘要，详细拆分可点开查看。四种借贷操作分别保留未保存草稿，避免错用方向或利息；再记时清空本笔金额、利息、备注、往来方与约定日期。

基础行为如下，原单关联程度仍需确认：

| 操作 | 本金方向 | 额外输入 |
| --- | --- | --- |
| 借入 | 对方的应付／负债账户 → 收款账户 | 可选约定还款日 |
| 借出 | 付款账户 → 对方的应收／资产账户 | 可选约定收回日 |
| 还款 | 付款账户 → 对方的应付／负债账户 | 可选实际支付利息 |
| 收款 | 对方的应收／资产账户 → 收款账户 | 可选实际收到利息 |

“对方账户”是用户在自己的账目中建立的往来记录，不访问对方银行账户。有息还款采用明确的含息文案；建议主金额标为“还款总额”，利息字段标为“包含利息（已计入总额）”，自动展示“偿还本金”。收回借款时可对应使用“收款总额”和“包含利息”。

例如偿还本金 1,000 元、利息 20 元，现金账户合计减少 1,020 元，负债本金减少 1,000 元，支出只增加利息 20 元。收到还款时同理，本金减少应收，实际利息计收入。利息只依据实际输入记录，不自动推算。

### 本金与含息总额的输入歧义

用户已通过付款账户逐笔余额与详情核对：本次测试版本的还款主金额为含息总额，实际资金减少该总额，往来本金抵减总额减利息。首页的还款行和利息支出行都会打开同一还款详情，属于同一笔业务的不同展示入口，没有在总额之外再次扣除这部分利息。这一结论针对实际验证的还款场景，不推断未测试的其他借贷输入行为。

同一测试业务的 XLSX 导出使用另一种表示：还款行已经是本金金额，利息另列为支出；两行相加才是实际付款。历史导入不得再从本金行扣除一次利息。文件没有专门的组合业务 ID，配对歧义及保留方式见 [导出专题](WACAI_EXPORT.md)。

用户明确提出文案改进：把单独的“利息”改为“包含利息”，避免把总额误读成本金。BesLedger 在输入、详情和列表中统一表达包含关系；建议用一条还款主记录展示总额，下方写“其中本金……，利息……”。利息报表可以单独列出利息组成项并跳回同一详情，但总额与组成项不能作为可相加的独立现金流水重复汇总。

应付详情中的正数表示仍欠对方，账户列表的负数表示负债，不能读成利息收益。报表中的利息支出与往来账户剩余本金也属于不同统计对象。

以下延用虚构金额，比较两种输入口径；假定原欠本金 1,000 元且没有其他往来：

| 输入含义 | 实际付款 | 偿还本金 | 利息支出 | 剩余本金 |
| --- | --- | --- | --- | --- |
| 本金 1,000 元，另付利息 20 元 | 1,020 元 | 1,000 元 | 20 元 | 0 元 |
| 含息总额 1,000 元，其中利息 20 元 | 1,000 元 | 980 元 | 20 元 | 20 元 |

依据借贷页简化反馈，输入页保留含息总额与简短的本金／利息摘要，按需展开“本次偿还本金”“本次利息”“实际付款合计”。正式实现中，只有往来余额数据完整、可靠时才展示“还款后欠款”，当前 UI 预览不模拟该余额。付款账户只减少实际合计，往来本金只按本金部分抵减，支出只统计利息；收款场景按相同拆分原则处理。不能既将总额全数作为转账，又再次扣除已包含的利息。

还款主入口按含息总额设计，以“包含利息”明确拆分；是否另外提供按本金输入的辅助方式后续再评估，不作为首期必需项。利息不能大于总额，等于总额表示只付利息、未偿还本金；显式填写零利息与尚未确定利息不能混为一谈。短信缺少拆分依据时保留待确认，不能替用户猜测。

只借入并全额归还上述虚构本金及利息后，往来余额应为零，相对借入前现金和净资产都减少 20 元。若实际现金减少了 1,020 元而往来仍欠 20 元，在没有其他变动的前提下就不符合这笔业务的预期结果，需要核查记录、汇总或软件计算。

本金转账与利息记录属于同一次用户操作：一起保存，修改和删除时保持一致，避免只改一半。内部可以分多条资金分录，但界面需能作为一笔操作查看。编辑本金和利息不应改变无关的原始借款记录。

第一版范围建议包含借贷入口、账户方向、可选日期、利息与合计、到期事项列表。自动计息、分期摊还、逾期罚息和复杂逐笔核销暂不纳入。PWA 关闭后的准时系统通知不作首期承诺；还款日的记录与系统推送能力分开。

## 退款与周期账

原消费详情保留原金额，显示累计退款并能展开每笔退款，退款详情可回到原单。实际到账账户独立选择；短信识别为退款时先形成候选，由用户确认类型及原单。

周期规则与已生成账单分开。编辑规则用于后续生成，历史记录可逐笔修改；修改规则前已到期却未生成的期次要先按明确规则处理。需要保留来源规则与期次，避免跨设备重复生成或覆盖手工修正。详细规则沿用 [专题设计](REFUNDS_AND_RECURRING.md)。

## 统计

用户认可挖财报表的时间选择、趋势图、分类与账户分布。截图可见全部／年／月／更多、前后期间切换、筛选、趋势与大类小类等维度，以及总额、占比、笔数、展开明细。官方完整维度不等于 BesLedger 首期全部照做。

建议先覆盖趋势、分类（大类／小类）和账户，成员、商家、标签、记录人后续按需求增加。页面顺序为时间与筛选 → 汇总 → 图表／排名 → 对应账单，返回时保留筛选和滚动位置。初版按趋势、分类和账户这三个维度实施，细节在开发中记录并验证。

建议统计规则如下，先明确含义再选择图表：

- 以交易发生时间筛选；粘贴时间、创建时间不改变所属期间。
- 期间净支出为期间支出减期间支出退款；净收入同理。跨月退款按实际退款日期进入当前期间，原单详情另展示累计退款，不暗中改写原月报表。
- 期间结余为净收入减净支出，不等于账户余额或净资产。
- 转账及借贷本金不计普通收入和支出，实际支付／收到的利息分别计支出／收入。
- 周期规则的未来期次不是已经发生的收支；只有已生成的正式账单参与实际报表。
- 汇总、图表、排名和下钻明细使用同一筛选与计算口径；待分类记录不从总数中消失。
- 净值为负或合计为零时，不用取绝对值或截断制造环形占比；改用有正负方向的条形图或原支出／退款拆分。
- 跨账户退款需区分“消费成本归属”与“实际资金流向”。账户支出图采用哪个口径、是否另外提供账户流入流出图，待确认。
- 平均值分母按自然期间还是已过天数、笔数是否分别计退款、占比的小数规则均需统一，不能仅凭参考图猜算法。

建议默认当前账本，另提供全部账本范围；是否记住上次选择待确认。全账本报表显示数据覆盖范围，未下载或未同步完成的账本应提示缺失，不显示为零。图表聚合与渲染解耦，暂不指定图表库。

## 多端与异常体验

当前 UI 预览使用虚构数据，覆盖首页、记一笔、分类选择、账户列表与详情、选择账户类型、添加账户、借贷、账单与退款、添加退款、事件与周期规则、统计、账本管理、设置和全部功能，共 16 个页面。提供手机、iPad 和电脑布局及浅色／深色外观。页面导航、账户类型选择及表单检查、示例短信预填、利息拆分、追加退款、周期规则与历史单笔分开编辑可演示；保存、云端下载与同步均为当前预览中的模拟状态，未连接真实账本或 GitHub。

预览用于确认视觉与交互，导航、分类共用和报表范围中的建议方案仍需结合用户反馈调整。后续正式实现继续按领域模型与数据验证推进，不把预览代码当作已完成的持久化、解析器或同步模块。预览及检查图片存放在会话目录，未复制个人财务截图到项目。

### 配色探索与初版基线

用户希望重新评估记账产品的适合配色，并讨论 BesSoftware 系列是否需要统一品牌色。已有预览沿用暖白与绿色，但这不是已确认的 BesLedger 品牌决策，也不能仅凭现有截图确定绿色最早来自哪个产品。

当前提供三套相同布局的配色供比较：墨蓝与暖灰白（推荐，沉稳、清晰）、森林绿与暖白（延续系列现有观感）、暖琥珀与米白（更接近个人纸质账本）。用户随后接受当前页面作为初版设计基线，实施先沿用墨蓝与暖灰白，保留暖橙记账入口；这不构成系列统一品牌色决定。收入／流入、错误等业务语义颜色独立于产品主色；浅色和深色外观分别适配，数字仍有符号与文字说明。

系列层面建议保留深绿作为母品牌识别色，用在 BesSoftware 入口及系列标识；各产品可按用途选择主色，共用字体层级、图标风格、间距和交互规范。这是本项目中的讨论建议，未修改 BesSoftware、BesFuel 或 BesTools 的设计，也未建立强制的跨项目规范。

手机优先单手记账；iPad 与电脑建议使用列表和编辑区并排布局，但字段语义、分类和统计一致。数字输入适配触屏与实体键盘；焦点、粘贴、软键盘遮挡、大字体和屏幕阅读标签需实机验证。

空账本提示创建账户并记第一笔；空报表区分“期间无记录”和“数据尚未下载”。同步失败保留本地可编辑数据；解析失败保留备注并允许手工填写；短信读取权限拒绝时继续提供粘贴。任何平台都不以连接 GitHub 或授予短信权限作为手工记账前提。

## 实施中细化的事项

1. 首页和导航沿用当前确认版，统计先做趋势、分类与账户；细部布局在真实运行中验证。
2. 内置分类与排序建议的实际使用反馈，以及分类是否跨账本共用。
3. 借贷是否关联某笔原借款、日期提醒的展示，以及是否需要额外的按本金输入方式；含息总额与“包含利息”的主入口文案已明确。
4. 信用卡账单日、还款日、额度是否首期需要；首次期初录入与后续余额校正的具体交互。
5. 共用账户遇到仅本地账本、仅云端账本时的余额展示与同步范围。
6. 连续记账保留哪些字段；缺少年份时怎样选择补账年份。

用户已允许这些细节由实施者合理决策、记录并落地，之后再根据反馈调整，不作为持续实施的阻塞项。明确功能及验收以 DELIVERY_SCOPE.md 为准。初版设计不包含真实财务截图，新增图片数量为 0。
