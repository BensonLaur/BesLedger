# 产品定位与初始范围

日期：2026-10-21。状态：初版设计已确认，进入完整交付准备；未定工程细节可在实施中合理决策并记录，验收以 DELIVERY_SCOPE.md 为准。

## 为谁解决什么问题

BesLedger 首先服务作者本人。作者有长期使用挖财记账的习惯，消费尽可能从一张银行卡扣款，已经开通银行交易短信提醒，常隔几天乃至半个月集中补记。

主要痛点是：粘贴短信后仍需逐笔调整交易日期和时间，同时核对金额、分类及账户。延迟补账时，录入日期与实际交易日期经常不同，时间识别是首要需求的一部分。

第一条核心流程是：复制一条短信 → 粘贴到记账页备注 → 预填账单草稿 → 核对或少量修改 → 确认保存 → 继续下一条。

## 已确定的方向

- 名称：BesLedger；中文展示名：Bes记账；属于 Bes 系列。
- 优先满足个人真实场景，以后开源并有真实反馈，再考虑更广泛的常见功能。
- 本轮交付 Web/PWA 和可安装 Android APK；兼顾 iPad 网页，iPad 原生安装包暂缓。
- 本地能够记账、查看、修改和导出，不强制注册或连接 GitHub。
- 首次使用从启用时点的账户余额／欠款开始记新账，旧账暂留挖财；历史迁移不作为第一版启用的前置条件。
- GitHub 私有仓库作为可选云端同步存储，账本在创建时就获得永久唯一 ID。
- 以“仅本地、已同步、待同步、仅云端”作为列表主状态，补充同步任务与异常提示。
- 识别原文保留在用户的账单草稿和记录中，方便追溯与修正。
- 手机界面下方“＋”进入记账页，分类名称与选择交互沿用熟悉的挖财习惯。
- 多个账本共用资金账户和余额；信用卡、自定义负债与应收应付往来纳入账户模型。
- 基础借贷记账纳入第一版，复用账户转账逻辑，支持借入、借出、还款、收款，并设计可选日期和利息输入。
- 如果法规、系统权限和发布渠道允许，增加读取短信并勾选识别；任何平台保留备注粘贴入口。

## 首个场景中的四项信息

| 字段 | 预期行为 |
| --- | --- |
| 分类 | 从商家、用途和用户规则提出候选；无法确定时保留待分类 |
| 资金账户 | 根据银行、卡尾号匹配已配置账户；常用账户作为明确的备用建议 |
| 金额 | 识别本次交易金额，区分短信中的账户余额、限额等其他数字 |
| 时间 | 提取交易月日与时分；缺少年份时依据补账上下文给出可确认的候选 |

分类识别的依据通常弱于金额和卡尾号，不能以一个总置信度掩盖某个字段的歧义。应分别展示“原文提取、规则推断、用户默认、缺失/冲突”等来源。

## 体验目标

- 对已适配的常见银行短信，尽量只需粘贴、扫一眼确认、保存。
- 常见样例单笔录入争取约 10 秒内完成，须通过真实设备和实际使用验证。
- 支持连续逐条补账，已经确认的补账年份等上下文可在当次操作中复用，但要保持可见、可修改。
- 原文解析在本地完成；第一阶段不需要把银行短信发送到外部大模型服务。

## 新增确认的个人场景

2026-10-21 补充：

- 同一笔支出可关联多次、部分退款；保留原金额，每笔退款拥有自己的发生时间和入账账户，原单与退款可相互查看。
- 原单详情展示累计退款和退款记录入口，明细中的退款有明确标记；退款入账账户可以不同于原付款账户。
- 周期记账用于公积金等固定入账，也考虑周期转账。周期规则可编辑，修改影响后续生成；历史已生成账单可在对应列表中逐笔修改。
- “从指定过去月份起批量调整”经用户最新反馈降为后续候选，不作为当前基础周期账的验收条件。

这些已纳入完整第一版，尚未实现；按实施阶段逐步完成，不因分阶段开发而省略。官方事实、截图观察与 BesLedger 建议分别记录在 [退款与周期记账](REFUNDS_AND_RECURRING.md)。

## 暂不扩展的范围

首期不以多人协作、家庭权限、商业账务、理财产品、OCR、复杂贷款管理或全银行模板覆盖为目标。短信先从作者常用银行卡通知格式验证；Android 原生读取属于条件性增强，持续监听与无人确认入账不作为当前承诺，详见 [短信访问边界](SMS_ACCESS.md)。

挖财历史账单迁入后续再评估；提前导出可用于私人备份和迁移格式调研，不改变先记新账的决定。从短信自动选择退款原单、批量粘贴多条短信的交互，均待后续讨论。跨账本共用账户已经确认，其同步范围和不完整数据下的余额展示仍需设计。“手动关联多次退款”已经是明确需求，不等于授权解析器自动确定退款归属。周期账历史批量重算暂缓。
