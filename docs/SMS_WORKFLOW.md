# 备注识别与银行短信粘贴录入

更新日期：2026-10-30。状态：已实现本地规则识别与明确字段自动填入，本轮更新本地 Web，并提供 0.1.4-test.1 安卓测试包；公开稳定版仍为 0.1.3。手写和银行通知共用记账页备注入口；Android 短信读取按平台条件另行处理。

## 使用背景与流程

作者尽量让消费从常用银行卡扣款，通过银行短信集中补记多天的交易。目标是从一条粘贴文本生成尽可能准确的账单草稿，减少金额、账户、分类和交易时间的重复输入。

确认的基本流程：备注中粘贴 → 本地解析 → 展示字段及依据 → 用户修正/确认 → 本地事务保存 → 如已为当前账本开启 GitHub 同步，进入待同步队列。确认保存前，解析结果只是草稿。

保留可编辑文本输入区，支持普通粘贴；“读取剪贴板”只能在用户主动操作下按平台能力增强，不能成为唯一入口，也不后台持续读取剪贴板。

备注识别提供自动与手动两种模式，默认手动；输入和粘贴都遵循当前选择，不会因粘贴而绕过关闭的自动开关。自动模式直接填明确字段并保护手动修正；手动模式只有用户主动采用时才替换识别字段。Android 原生读取先筛选范围、展示候选、由用户勾选，再进入同一草稿流程；访问条件、未选数据处理和平台差异见 [短信访问边界](SMS_ACCESS.md)。

## 手写备注与金额优先

备注下方提供“自动识别”开关，关闭时点击“识别备注”，开启后输入停顿约 350 毫秒识别最新备注，也可点击“立即识别”。输入“停车费10元”“停车费10块”“停车费 10 元”后，自动模式把有明确货币单位的唯一金额和同类型的唯一分类直接填入草稿，并收成可展开的简短提示，可直接保存；手动模式仍先预览再点击“采用并继续核对”。修改备注后旧预览立即失效，自动模式合并连续输入，只处理最后一版，中文输入法组词期间不识别。手动输入金额、点击数字键盘、手动选择分类、候选或新建分类后，各字段分别受保护，清空也不会被自动重填；编辑旧账时已有值默认保护。新备注不明确时只撤回上一版自动值，不删除手动值。

开关记在当前浏览器/应用的本地界面偏好中，不写账本、不上传或跨设备同步。存储受限时本次仍可切换并给出提示。开启自动后可识别当前新草稿；打开已有账目时不自动弹预览，编辑备注后才识别。采用、保留、清空、关闭自动、切换类型及离开编辑页会清理未运行的识别。若识别尚在等待时点击保存，先识别最新文本，明确字段直接保存，不确定字段继续选择。无单位推断、多金额、多分类、未确认的类型、年份/时间及账户变化在面板展开核对；点击金额或分类候选可直接选定，信息齐全后不再强制点“采用”。确认其余信息也不覆盖后来手改的字段。自动模式不擅自改动时间、类型或资金账户。

- 金额独立于交易类型提取，支持元、块/块钱、圆、人民币、¥/￥、RMB/CNY、千分位、全半角、空白、小数，以及常见中文金额和元角分组合。“十块五”可识别为 10.50 元；“一百二”等口语歧义、负数、零金额、超出分精度或安全范围时不自动填入。内部以整数和 BigInt 转换，不用浮点或四舍五入掩盖错误。
- 有明确用途时，“停车费10”“午餐 25”等无单位写法可按元提出候选，并提示核对。仅输入数字也可按元核对。日期、时间、明确标注的尾号/订单号/手机号、数量与时长不当金额。
- 余额、单价、原价、优惠、额度、预算和找零单独处理；唯一明确的“实付、实际扣款、合计”等优先。多个交易金额保留各候选，由用户选择，不自动相加、减优惠或计算单价。“余额在前，交易在后”也可识别；备注余额只作核对。
- 用途同义词按内置分类映射，例如停车/泊车/车位费，打车/出租车/的士/滴滴，早餐/早饭，话费/手机充值。单一明确候选可随采用填入；无可靠时间的餐厅、超市或多个用途保留多个候选。支付平台名不能代表资金账户或消费分类，显式商户规则仍优先。
- 包点/包點、包子、豆浆/豆漿、肠粉/腸粉、食堂、餐厅、吃饭等先识别为餐饮用途，再按原文唯一有效时间推荐餐次：05:00–10:59 早餐、11:00–14:59 午餐、17:00–20:59 晚餐、21:00–次日 04:59 夜宵。15:00–16:59、无时间、多时间或无效日期时保留四种餐次候选，不用当前补账时间猜测。文字明写的餐次、具体分类及用户商户规则优先；推荐依据就近显示，仍由用户确认。仅有“08:20”这类时间可辅助分类，但不据此改动草稿日期。
- 收入和退款分别处理；转账、借还、未支付或失败的交易须核对类型，外币不按人民币填入。不认识或未写的账户、时间及金额保留当前手动字段，不用推测结果覆盖。

人工列出的输入与预期见 [备注识别测试](../tests/recognition-notes.test.ts)，涵盖常见输入、金额边界、分类同义词及旧短信回归；[浏览器流程](../tests/e2e/note-recognition.spec.ts) 验证确认、候选选择、取消、编辑后预览失效、保存重开与小屏布局。全部样例虚构，工资示例为 6000 元。

## 本地解析顺序

1. 保留原文，建立用于解析的规范化副本，处理空格、全半角符号和千分位等差异。
2. 识别银行模板、卡尾号、交易方向、商家/用途、交易金额、余额、日期时间片段。
3. 根据银行与尾号匹配资金账户；根据用户已确认的商家规则建议分类。
4. 结合当次补账上下文处理缺少年份等信息，标记推断来源。
5. 返回字段候选、歧义和缺失项，用户确认后才形成正式记录。

优先从作者常用的工商银行通知格式验证。模板提取、商家分类和用户偏好分开实现，避免用一个宽泛正则直接生成最终账单。后续遇到新模板再增加适配，不要求一开始覆盖所有银行。

## 四项核心信息

| 信息 | 可靠依据 | 不足时的行为 |
| --- | --- | --- |
| 交易金额 | 与支出、收入、退款等语义关联的金额 | 缺失时不使用余额补齐，提示补填 |
| 资金账户 | 银行标识、卡尾号及本地账户映射 | 未匹配或多候选时提示选择 |
| 交易时间 | 原文明示的年月日、时分及补账上下文 | 标记缺失或推断，允许修正 |
| 分类 | 商家、用途和用户确认过的映射规则 | 无依据时待分类；弱依据只给候选 |

保留每个字段的来源，例如原文片段、命中的模板/规则、用户默认值或手动修改。不要把字段级不确定性压缩成一个看似精确的整体置信分数。

## 日期与时间

- 交易发生时间与记录创建时间分别保存。补录历史短信时，粘贴时间不能覆盖原文月日时分。
- 无年份的短信保留原始月日时分；结合明确的补账年份或上下文提出候选。首次使用缺年候选时要让用户确认，确认的年份可在当次补账流程中复用。
- 跨年时可以提出上年候选，但不能仅凭“当前日期”静默判定；导入更久以前的短信时尤其需要确认年份。
- 对无效日期、未来日期、缺失时间或含多个时间的文本给出提示。无效日期不能自动滚动到下一个月。
- 首个国内场景默认使用 Asia/Shanghai。日期字段、时区与推断依据保持可追溯。

## 账户、渠道、金额和余额

- “支付宝”“财付通”出现在银行扣款短信中时可能只是支付渠道，不能据此把资金账户改成支付宝或微信余额。
- 银行与卡尾号的明确证据优先于常用账户偏好。明确尾号与默认账户不一致时，不静默使用默认账户。
- 同尾号多账户或缺少银行标识时保留候选，不把尾号当成全局唯一账户 ID。
- 本次交易金额与交易后余额分别提取。短信余额可作为后续核对证据，不在保存草稿时直接覆盖账本计算出的账户余额。
- 初期人民币金额以整数分表示；原始小数文本准确转换，禁止先转浮点再随意四舍五入掩盖解析错误。

## 补账时快速调整账户起算时间

记账页发现实际使用的资金账户起算时间晚于这笔账时，保留历史查询说明，并在提示后提供“调整起算时间”。转账或借贷涉及两端时，分别列出需要调整的账户，不能因调整其中一端就隐藏另一端的提示。

弹框显示账户名称、当前起算时间和可编辑时间；推荐这笔账已采用日期的当天 00:00，点击推荐只填入字段，确认后才保存。没有采用短信结果时以当前草稿的发生日期为准，不擅自采用尚待核对的识别日期。起始金额不变，已有流水按新起算点重算余额；弹框就近提醒用户核对起始金额是否适用于新时间。

确认只修改目标账户的时间和版本，保留账户其他信息与当前未保存的金额、分类、账户、备注、实际发生时间。提示按更新后的账户重新计算；若手动时间仍晚于这笔账，则继续显示历史提示。分钟值先补齐秒再比较，恰好等于起算点的交易不能误报。取消不写入，账户已变更或跨窗口保存竞争须重开核对，不覆盖已有更改。

## 分类与退款

分类先采用商家/用途规则和用户显式确认的偏好。例如已经配置“示例包点 → 餐饮”，即可给出餐饮候选；仅出现支付平台名时，不足以确定消费类别。

“收入（退款……）”可提取为资金流入并标记退款候选，不能直接落成普通收入。用户已确认需要一笔支出关联多次退款，并参考挖财的原单、退款列表与退款详情跳转。保存前可人工选择原单，实际退款账户按短信及用户确认处理；从短信自动选定原单仍待讨论。统计与数据关系见 [退款与周期记账](REFUNDS_AND_RECURRING.md)，当前虚构解析样例中的 `refundTreatment` 确认项继续保留。

规则提取不需要外部大模型。若以后确有无法覆盖的文本，再单独讨论可选识别服务、隐私与费用，不能默认上传银行短信。

## 借贷本金与利息

当短信明示的是还款实际扣款总额时，不能把它直接当作本金，再叠加用户填写的利息。识别结果应保留“付款总额”的含义；原文没有本金／利息拆分时标为待确认，在用户补充利息后预览本金、利息、合计与还款后欠款。收回借款的到账总额同理。

转账、信用卡还款和私人借贷的用途不清时不能只凭资金方向自动确定。本金不计普通收支，实际利息分别计入支出或收入。两种金额输入口径和账户验收关系见 [产品设计草案](PRODUCT_DESIGN.md)。

## 重复与连续补账

同一原文和交易特征再次出现时提示疑似重复，展示已有记录供核对。不要只因同日同金额就自动删除或拒绝保存，真实交易可能重复发生。

用户确认保存后再清理当前草稿；保存失败保留输入和修正结果。连续逐条粘贴属于首要场景，多条短信一次粘贴的批量交互留待后续确认。

## 示例与未来验收

[虚构样例 JSON](examples/sms-recognition-cases.json) 包含输入上下文、字段预期与待确认项。所有卡尾号、商家、金额和余额都为改写的虚构数据，不是原始交易记录；字段结构是讨论和测试素材，不代表最终公开 API。

后续验收优先检查：

- 消费金额不会取成余额，银行卡账户不会取成支付渠道。
- 原文时间可直接预填；缺年、跨年和无效日期不被悄悄修正。
- 退款与普通收入可区分，未知分类和账户歧义可人工处理。
- 保存、刷新、重启后保留用户确认的内容；重复提交不产生意外重复记录。
- 在真实 iPad、Android 和电脑浏览器上，评估粘贴、修正与保存所需时间。
