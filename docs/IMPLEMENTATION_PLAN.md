## 启动判断与第一个交付

可以开始分阶段实施，不需要先补齐全部页面细节或取得更多私人历史账单。第一个可运行增量用于验证核心记账流程，不等同于已经包含全部已确认功能的完整第一版。

### 可以采用的工作默认值

既有明确设计按专题文档执行；其余细节由实施者选择合理默认值并记录，避免反复阻塞。完整交付清单见 [DELIVERY_SCOPE.md](DELIVERY_SCOPE.md)，不能停在第一个增量。

- 共用一套分类，每个账本单独配置常用项和排序；先提供已知的常用分类并允许增改，不把导出里出现过的类别当成完整默认分类库。
- 统计先覆盖收支与结余趋势、大小类统计、账户统计；其他维度以后按实际需要加入。
- 首页沿用已确认的轻立体月历、明细联动、预算水印、快捷浮层及“＋ 记一笔”。新建日期和时间按 HOME_DESIGN.md 执行。
- “保存”返回来源页面，“再记”保存后保留记账页。清空本笔金额、备注和解析结果，保留账本及可见的补账年份上下文；不静默沿用上一条短信的账户、类别或发生时间。

### 实施顺序

1. 明确最小领域模型与计算约束：账本、共用账户、期初状态、分类、业务操作及资金变动。为组合借贷、退款原单和周期来源保留稳定关系；不能把导出表的一行直接等同于内部的一笔完整业务。
2. 建立 Vue／TypeScript／Vite 工程和本地页面，先支持创建账本、建立账户与期初余额，以及收入、支出、转账的新增、编辑和删除。
3. 接入备注粘贴与常用银行模板，完成金额、账户、时间及分类候选的预填、确认、连续补账和重复提示。
4. 接入本地持久化、账单列表、账户余额计算及带版本和稳定关系的数据备份／恢复，形成可反复使用的本地流程。
5. 用虚构样例完成自动化验证，再在实际 Android 和 iPad 上核对粘贴、软键盘、刷新恢复及离线行为；实机结果与桌面模拟结果分别记录。

第一个交付的完成标准是：能够从期初状态出发，粘贴并修正一笔记录，保存后在明细和账户余额中得到一致结果，重新打开仍可读取，导出后能够恢复。具体金额和日期计算必须有测试支撑，界面可运行不代表计算已通过验证。

### 需要先解决的工程决定

- 本地落盘加密、解锁和密钥恢复在持久化实现前明确，不能仅因云端将会加密就宣称本地已加密。未定型的界面原型使用虚构数据。
- 共用账户与仅本地／仅云端账本并存时的余额完整性、同步范围在 M2 前明确；本地阶段先使用本机完整数据，不伪造云端状态或完整余额。
- 金额、期初边界、转账双端、保存与修改的一致性在领域层定义并验证，不留给页面各自计算。

基础借贷、关联退款、周期账及基础统计随后作为 M1 的增量逐项加入，仍属于第一版设计范围。GitHub 登录、私有数据仓库和加密同步在 M2 完成，Android APK 与 Web 交付在后续阶段完成，均属于本轮总目标。短信读取保持条件性增强，挖财历史导入暂缓。创建 commit、远程仓库、推送和发布继续按用户当次授权执行。

## M1：本地单笔录入闭环

搭建 Vue/TypeScript/Vite 工程，锁定运行环境和依赖；先验证常用银行短信从粘贴、字段预填、人工修正到本地保存的完整流程。

首次启用按用户确认的“账户期初状态＋新账”推进，旧账暂留挖财，历史导入不阻塞第一版。已取得的导出文件用于私人备份和迁移格式调研；本应用自身的导出恢复继续纳入首个闭环。

建议先确定：资金账户的最小模型、常用类别、缺少年份的补账上下文、退款草稿行为、本地落盘加密策略。跨账本共用资金账户已经确认，须在模型定型前明确账户级同步范围及余额完整性。

数据模型同时考虑已确认的多次关联退款、周期规则与生成账单的来源关系。两个功能的具体实现排期另行讨论，周期账先采用“修改未来规则＋逐笔修正历史”，不把追溯批量调整纳入首个闭环。

第一版范围包含收入、支出、转账、基础借贷，分步实现不等于删除后者。基础借贷复用转账能力，增加往来账户选择、可选日期和利息；优先验证本金不计收支、利息单独统计以及组合操作的一致保存。普通转账管理私人欠款的已有习惯继续保留。

验收：

- 金额、账户、时间按样例可解释地识别；分类不确定时有明确候选或待分类。
- 交易金额和余额、交易时间和创建时间互不混淆。
- 账户期初余额／欠款有明确起算时点，不计当日收支，不因多账本共用而重复累计；补录已包含在期初中的历史交易时有明确处理。
- 借贷本金与利息的账户变化、收支统计一致；修改、删除组合操作后不遗留本金或利息的半笔记录。
- 分别验证“本金另加利息”和“总额内含利息”的输入口径：实际资金变动等于本金加利息，往来余额只按本金抵减；完整借还后欠款归零、净资产变化等于利息成本。覆盖只付利息和利息大于总额的边界，短信扣款总额不重复加息。
- 保存结果和待同步操作一致落盘；无云端连接时正常记账。
- 刷新和重新打开后数据仍在，能够导出并恢复；PWA 安装与离线资源正常。
- iPad、Android 和电脑均能完成输入、修正与保存，记录真实体验问题。

## M2：验证 GitHub 加密同步

先完成真实 GitHub 登录与专用私有数据仓库创建/选择，再验证账本发现、首次上传、另一设备下载、编辑回传及四种主状态。PAT 可辅助调试，但不能作为登录功能最终替代。

验收：

- 云端仅保存约定的密文和必要元数据，凭证与解密密钥不进入仓库。
- 重复重试不重复入账；冲突不静默丢弃；下载和写入的中间状态不可作为完整账本使用。
- 断网、权限失效、清除本机副本后的恢复都有可理解的状态和恢复路径。
- 无法查询云端时仍可使用本地账本，并正确显示最后确认时间。
- 用两台实际设备验证同步，而非只依据单浏览器模拟得出结论。

## M3：Web 与 Android 交付及验证

完成 Capacitor Android 工程、原生存储适配、可安装签名 APK、Web/PWA 生产构建和部署配置；验证离线启动、重启持久化、更新迁移、键盘/返回键和双端同步。提供实际产物、校验值、测试结果和使用说明。自动化、模拟器、实机验收分别记录；没有接入真机时不能宣称真机通过。完整第一版交付后再依据个人补账反馈迭代，历史数据迁移继续暂缓。

Android 短信读取是已提出的条件性需求，在 APK 实施中验证目标设备与分发渠道的可行性。验证权限申请、最小查询范围、勾选导入、拒绝与撤回，不能把“具备 READ_SMS API”当作“所有手机和商店都可发布”。不满足条件时交付备注粘贴流程。

开源与远程发布另按用户授权执行。以后收到真实用户反馈，再讨论普遍需求，避免把首期变成完整商业记账产品的功能清单。

## 验证策略

文档阶段只检查内容一致性、链接、样例格式和 CRLF。应用阶段用 Vitest 验证解析与业务规则，用 Playwright 验证浏览器交互和故障场景，结合真实移动设备验证生命周期及存储行为。

参考软件的功能只作为比较依据；详细来源见 [参考资料](REFERENCES.md)。
