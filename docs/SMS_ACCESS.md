# 短信读取与发布边界

核对日期：2026-10-21。适用场景：中国大陆个人记账工具，比较手动粘贴与 Android 短信读取。以下是根据公开规则形成的产品和工程判断，不是监管批准或正式法律意见；具体发行版本仍须结合实际数据流和渠道核实。

## 当前结论与需求

所查现行规则未发现对“短信记账”这一功能的一概禁止。需要分别判断个人信息处理是否合法、操作系统是否开放能力、分发渠道是否允许权限。开源并不豁免上述条件，权限限制也不意味着整个开源项目不能开发。

用户已确认：备注粘贴自动识别分类、资金账户、金额、交易时间必须保留；如果法规、系统和发布渠道允许，也希望读取短信，勾选后识别。前者是通用入口，后者是有条件的 Android 原生增强。暂不承诺收到短信后无人确认即正式入账。

## 中国大陆规则

[《个人信息保护法》](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm) 第 5、6 条要求合法、必要和最小范围；第 14—17 条涉及知情同意、撤回和告知；第 28—30 条对金融账户等敏感信息提出更严格条件。因此系统授权弹窗不能替代完整的个人信息处理依据和必要性判断。本地解析可减少外传，但不能简单推导为一切处理均无合规义务。

该法第 72 条对自然人因个人或家庭事务处理信息设有例外。自己使用与公开提供应用应分别判断；不能把自用例外自动扩展成开发者面向其他用户提供服务的全面免责。

[《常见类型移动互联网应用程序必要个人信息范围规定》](https://www.cac.gov.cn/2021-03/22/c_1617990997054277.htm) 要求不得因拒绝非必要信息而拒绝基本功能，不是授予任意读取短信的许可。[2022 年应用程序信息服务管理规定](https://www.cac.gov.cn/2022-06/14/c_1656821626455324.htm) 第 12 条同样强调必要性和基本功能可用。

[网信办 2026 年个人信息政策问答](https://www.cac.gov.cn/2026-01/09/c_1769688003183197.htm) 将短信、消费记录等列入个人信息讨论范围。银行短信可能涉及金融账户等敏感信息，BesLedger 应按敏感财务内容保护，不保留无关验证码和私人通信。

另外检索到的 [2026 年应用程序个人信息收集使用规定](https://www.cac.gov.cn/2026-01/10/c_1769603446094128.htm) 页面是征求意见稿，不将其当作已经生效的禁令。

## 平台能力与渠道

| 入口 | 能力判断 | 对 BesLedger 的影响 |
| --- | --- | --- |
| 浏览器／PWA | 无通用短信箱读取能力；WebOTP 只处理符合要求的验证码短信 | 保留用户在备注中粘贴，不承诺安装 PWA 后可读取银行短信 |
| Android 原生 | 存在 READ_SMS；属于受严格限制的权限，还涉及安装程序许可与运行时授权 | 需要原生适配、系统版本和真机验证，不能只做一个同意弹窗 |
| Google Play | 现行政策列出 SMS-based money management 例外，要求核心功能、替代方案条件及审核批准 | 有申请路径，但 BesLedger 尚未获批；存在粘贴入口也不能自行认定必定符合例外 |
| 国内 Android 应用商店 | 需按具体商店、应用类型及版本核实 | 本轮没有确认某一家渠道必定接受，不以 Play 规则替代国内审核 |
| 中国大陆普通 iPad／iOS 应用 | 不作为通用短信箱读取入口；苹果的特定运营商短信接口有地区、默认应用等限制 | 当前按粘贴支持；Android 导入后的已保存账目可通过可选同步到其他设备 |

依据：[Android READ_SMS 文档](https://developer.android.com/reference/android/Manifest.permission#READ_SMS)、[Google Play 短信权限政策](https://support.google.com/googleplay/android-developer/answer/10208820?hl=en)、[WebOTP 官方说明](https://developer.chrome.com/docs/identity/web-apis/web-otp)、[Apple TelephonyMessagingKit](https://developer.apple.com/documentation/TelephonyMessagingKit)。苹果新接口不能被泛化成所有地区、所有普通记账应用都能读取系统历史短信。

Google Play 的例外属于平台政策，不能证明中国法下某个具体实现已合规。自行构建安装与商店上架条件也不同，不把侧载当成法律或系统权限的豁免。

## 建议的读取流程

1. 用户主动进入“从短信导入”，选择日期范围和银行发送方范围。
2. 展示读取目的、范围、处理位置与保存方式，按适用要求取得同意，再请求系统权限。
3. 在平台允许的范围内查询候选，优先用日期和发送方收窄读取，排除验证码、营销及私人短信。
4. 展示候选供勾选，使用与备注粘贴共用的本地解析器生成账单草稿。
5. 用户核对字段与重复提示后保存；未选短信不持久化、不进入日志或同步数据。
6. 提供关闭入口；撤回权限后停止读取，手动记账和粘贴继续可用。

勾选页通常是应用自己展示读取结果，并不意味着系统只授权应用看到勾选的那几条。说明中必须如实区分“为显示候选而读取”与“用户确认后保存”，不宣传虚假的逐条系统授权。

新短信接收可以另行评估为生成待确认草稿；不能从一次导入授权扩展成持续后台读取。所需权限、后台限制与渠道条件单独验证。不上送整箱短信，不将无关内容发送到外部 AI，也不通过其他高权限接口规避被拒绝的短信访问。

## 同步与开源

识别与 GitHub 同步分别开启。开启同步后，用户确认保存的账单以及保留在备注中的短信原文可能随账本上传，应在功能说明中明确；不能在这种情况下声称短信永不离开设备。

GitHub 私有仓库和客户端加密属于保护措施，不能直接等同于匿名化或自动排除跨境处理问题。对外提供同步服务时，应依实际角色和数据流核对跨境规则；自用、开源源码分发、托管服务分别判断。未启用同步时保持本地流程完整。

公开项目仅保留虚构短信样例，不收集用户银行短信作为默认遥测、错误日志或公开 issue 附件。现阶段继续产品设计与本地开发，发布前再核对目标渠道、数据流、隐私说明和适用手续。

## 实施顺序

先做通用备注粘贴闭环，并在核心之外定义短信来源适配接口。Android 原生读取作为独立可行性验证项：确定目标设备与渠道，验证权限、最小查询范围和撤回行为，再决定交付形式。原生入口可评估 Capacitor 加 Android 插件，不必为此重写跨端业务核心。

权限或审核条件不满足时，该发行版本继续提供备注粘贴；支持读取的版本也保留同一粘贴入口。
