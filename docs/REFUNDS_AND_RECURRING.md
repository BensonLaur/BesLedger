日期：2026-10-21。依据：挖财官方帮助、开发者公开更新记录，以及用户本轮提供的退款与周期账截图。未操作用户的挖财账户，当前只记录需求和技术约束，没有实现功能。

## 退款：已核实的参考行为

[官方退款说明](https://jz.wacaijizhang.com/guide/record/record_turnback.html) 确认：一笔原单可关联多笔退款，也可独立记退款；支出退款抵减支出，收入退款抵减收入，相关统计包含退款。

用户提供的四张截图进一步展示：

1. 明细中原支出和各次退款分别列出，退款带正向金额和“退款”标记。
2. 原单详情保留原支出金额，另有累计退款入口。
3. 点击入口打开退款记录列表，显示各笔退款的发生时间和金额，可以继续进入详情。
4. 退款详情提供返回原账单的入口，退款与原单的资金账户可以不同。
5. 交易发生时间与记录创建时间分别展示，补记不会抹去实际发生时间。

截图原始金额、账户名称和图片不复制进本项目，公开文档采用规则描述或虚构算例。

## BesLedger 退款需求

采用“一笔原支出关联多笔独立退款”的关系。保留原始支出金额，每笔退款独立保存金额、时间、分类、实际入账账户与可选原单 ID。

界面参考上述列表和跳转路径。退款账户使用“退款入账账户”文案，避免继续使用容易混淆的“付款账户”。可考虑在原单详情额外展示净支出，但这一展示细节属于 BesLedger 建议。

例如虚构支出 1,000 元，分别退款 200 元和 150 元：原单仍为 1,000 元，累计退款为 350 元，关联后的净支出为 650 元。净额是派生值，不能再与原单和退款重复入账。

退款进入另一个资金账户时，增加实际收款账户的余额；不能机械增加原付款账户，或在原付款是信用账户时自动减少原欠款。资金变动与费用统计应分别计算。

用户希望购车相关返现和补贴能关联原支出，以观察实际成本。是否按退款抵减支出由用户的统计口径决定，不能仅从短信出现“补贴”自动推断；来源和发生时间继续保留。

### 统计区间

官方提醒原单与退款须处在同一统计区间才能合并观察抵减结果。由此不能推断“关联后就会自动改写原消费月份”。

BesLedger 建议保留真实发生日期：按月份查看资金发生额，按原单查看所有关联退款后的净成本。跨月退款可能使退款月份的净支出降低甚至为负；不要为了平滑月报而改动退款日期。

### 待实现前确认

- 退款超过原单金额时的处理、原单被删除时的关系处理。
- 原单类别被修改后，退款类别是否跟随；跨币种和跨账本暂不默认支持。
- 识别退款短信后可由用户选择原单；自动匹配原单的规则与体验另行讨论。

## 周期账：已核实的参考行为

[官方周期账说明](https://jz.wacaijizhang.com/guide/recycle/recycle.html) 区分规则与生成记录：改规则影响修改后的生成，已生成账单不变；编辑某笔历史账单不改变规则。支持收入、支出、转账和借贷等类型。

帮助还列出规则起止日期、周期与入账时刻、暂停恢复及两种删除范围。开始日期可选过去时间，不等于编辑时可重算历史。[iOS 开发者更新记录](https://apps.apple.com/cn/app/%E6%8C%96%E8%B4%A2%E8%AE%B0%E8%B4%A6-ai%E8%87%AA%E5%8A%A8%E8%AE%B0%E8%B4%A6/id1544045905) 的 13.1.5 也说明修改会影响未来入账。

本轮未找到官方支持“选择过去某月，批量改写已生成账单”的明确说明；已明确记录的编辑方式保留历史。

用户最新截图显示规则管理列表、规则编辑表单和该规则的历史生成列表；用户同时确认历史记错的记录可以单独修改。截图中的原有开始日期不应被当作金额修改的生效日期。

## BesLedger 周期账范围

先支持个人的固定周期入账与转账场景：

1. 管理规则，显示金额、周期、账户及下次计划入账时间。
2. 修改规则的金额等字段时，明确提示后续生效，保留已经生成的历史账单。
3. 从规则进入它生成的账单列表，逐笔查看和修正历史；单笔修改不改变未来规则。
4. 基础流程验证后再根据实际使用讨论更多周期、暂停恢复及删除交互。

指定过去月份批量调整、历史批量重算和复杂例外规则暂缓，不作为当前验收条件。未来确有重复劳动时再评估。

### 最小数据关系与生命周期

建议生成账单至少携带来源类型、来源规则 ID、稳定期次标识，并保留生成时的字段值。字段命名与最终 schema 在实现时确定。

- 规则 ID 用于从规则查询历史；期次标识用于区分同一规则的不同发生次数。
- 同一期次的标识不随金额修改、手动修正或设备变化而改变；多设备生成和网络重试可据此去重。
- 手动修正历史金额、时间或账户后，重新同步不能再用当前规则把它覆盖回去。
- 规则停用或记录删除要保留必要标记，避免到期补齐时又生成已明确跳过的记录。

PWA 可在打开时按计划日期补齐到期记录，实际创建时间另记。修改规则前，需要先处理已到期未生成的期次，例如先按旧规则补齐，再修改未来规则；具体方案在实现时验证。这样不会因用户两个月没打开应用，就把新金额错误地套到全部旧期次。

若以后要求应用始终关闭也由云端定时入账，需要另行评估执行服务；本轮不因此增加服务器方案。

## 后续验证重点

- 原单、多次退款和累计金额一致；退款跨账户时只影响实际资金账户。
- 月度统计与关联净成本能分别解释，退款不被重复算作普通收入。
- 改周期规则不改历史，改历史单笔不改未来规则，原始来源关系仍在。
- 同一期次跨设备或重试只生成一笔；已经手动修正或删除的记录不被自动恢复。
- 历史批量调整保持暂缓，后续新增需求再独立记录。
